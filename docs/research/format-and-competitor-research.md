## Format matrix and adapter guidance

| Format | Plaintext schema / encoding | Encrypted variant and limits | Adapter guidance / synthetic fixture |
|---|---|---|---|
| Standard `otpauth://` | URI text, UTF-8; `totp`/`hotp`, `secret`, issuer/account label, optional `algorithm`, `digits`, `period`/`counter`. Ente’s exporter writes one URI per line. | No encryption in the URI itself. | First-class generic adapter. Parse URI before provider-specific detection; normalize Base32 and preserve explicit algorithm/digits/period/counter. |
| Ente Auth | `mobile/apps/auth/lib/models/export/ente.dart` documents encrypted JSON v1; decrypted payload is newline-separated raw `otpauth://` lines. Object fields: `version`, `kdfParams { memLimit, opsLimit, salt }`, `encryptedData`, `encryptionNonce`; Base64 strings. | Argon2id (libsodium parameters recorded in JSON) + XChaCha20-Poly1305 secret stream. Password required; no bypass. Current code derives with stored memory/ops limits and decrypts using stored nonce/header. | Support plaintext URI-list directly. For encrypted Ente JSON, implement a separate adapter only after crypto test vectors are generated; otherwise return `UnsupportedEncryptedFormat`. Do not confuse Ente’s local backup with server sync. |
| Aegis | UTF-8 JSON outer `{version:1, header:{slots:null, params:null}, db:{version:1..3, entries:[...], groups:[...], icons_optimized}}`. Entry fields include `type`, `uuid`, `name`, `issuer`, `info`; `info` includes Base32 `secret`, `algo`, `digits`, and TOTP `period` or HOTP `counter`. | Encrypted outer JSON has `header.slots` and `header.params`; Aegis source uses AES/GCM/NoPadding, 32-byte key, 12-byte nonce, 16-byte tag; password slots use scrypt `N=32768,r=8,p=1`, hex-encoded values. | Plain parser is safe to implement independently. Encrypted adapter requires exact password-slot and AES-GCM handling plus vectors; reject without password. Validate database/OTP versions and fail closed on unsupported parameters. |
| deskOTP | Plain backup is Aegis-shaped but `db` is deskOTP’s account DB. `internal/parser/deskotp.go` maps `entries[]` with `type`, `name`, `issuer`, `info.secret/algo/digits/period/counter`. Supports TOTP/HOTP/Steam; unknown types are skipped by upstream parser. | Encrypted deskOTP uses outer `header.slots` plus `data` (Base64 AES-256-GCM ciphertext), with `data.params` nonce/tag semantics; it is intentionally distinguishable from Aegis encrypted `db`. Password slot recovery reuses the Aegis-shaped scrypt/AES-GCM structure. | Detection order: deskOTP encrypted (`data` present, `db` absent) before Aegis encrypted. The source README says the format extends Aegis; treat this as schema compatibility, not code license compatibility. Upstream’s Steam mapping is fixed SHA1/5 digits/30 seconds; expose it as non-standard `steam`, never silently convert to ordinary TOTP. Current source uses an in-memory key cache and a user-config storage file with 0600 intent; no standalone `vault.key` file was found in the inspected tree. If AUTHENTICATOR DESK adds a sidecar key, document same-user trust, ACLs, and recovery semantics explicitly. |
| 2FAS | JSON `BackupContent`: `services[]`, `groups[]`, `updatedAt`, `schemaVersion` (current source constant 4), app metadata, optional `servicesEncrypted`, `reference`. `BackupService` has `name`, `secret`, nested `otp { link,label,account,issuer,digits,period,algorithm,counter,tokenType }`, `groupId`, and ordering/icon metadata. | Encrypted services/reference are separate strings. `DataEncrypted` is `base64(ciphertext):base64(salt):base64(iv)`. Current source derives AES key with PBKDF2-HMAC-SHA256, 10,000 iterations, then AES/GCM/NoPadding; a raw key can also be supplied. | Implement plaintext schemas 1–4 with defaults (`SHA1`, 6 digits, 30 seconds, absent `tokenType` => TOTP) and reject `reference`/`servicesEncrypted` unless a dedicated password adapter is present. Never read outer service `type` as OTP type; use nested `otp.tokenType`. |
| Google Authenticator migration | `otpauth-migration://offline?data=...` carries a protobuf `MigrationPayload`. Ente’s pinned `mobile/apps/auth/protos/googleauth.proto` defines nested `OtpParameters { secret bytes, name, issuer, algorithm SHA1/SHA256/SHA512, digits 6/8, type HOTP/TOTP, counter }`; migration has batch index/size and version fields in generated code/parser. Binary payload is Base64 in URI. | Transfer payload itself is not a password-encrypted backup; it is a QR transport. | Implement a bounded protobuf decoder (maximum payload/accounts/secret bytes), multipart batch assembly, strict UTF-8 and Base32 conversion. The Google Key URI wiki is not the migration protobuf specification; retain both references separately. |
| andOTP | Plain backup is a UTF-8 JSON array. Each object has Base32 `secret` (padding may be present), `issuer`, `label`, `digits`, `type` (`TOTP`,`HOTP`,`STEAM`), `algorithm`, optional `period` or `counter`, plus UI fields such as `tags`/thumbnail/usage. | `.aes` backup is a binary envelope: 4-byte big-endian iteration count (random 140,000–160,000), 16-byte salt, then AES/GCM ciphertext whose first 12 bytes are IV. PBKDF2WithHmacSHA1 derives a 256-bit key. `.gpg` is OpenPGP. | Plain adapter is straightforward and legacy-compatible. Encrypted `.aes` and `.gpg` require exact crypto implementations and password handling; reject without password and do not infer from extension alone. Steam uses fixed SHA1/5/30 semantics. |
| FreeOTP | Current FreeOTP 2.x backup is not a portable plaintext token schema. `BACKUP.md` says token data is encrypted in SharedPreferences XML with a master key in Android Keystore. `TokenPersistence` stores serialized backup map entries and token data; external backup is Java object serialization of the preference map. | Restore requires the master password; `MasterKey` uses PBKDF2-HMAC-SHA512 (fallback SHA1), 100,000 iterations, 32-byte salt and AES/GCM encrypted key material. The Android Keystore master key is the intended extraction boundary. | Do not claim current FreeOTP import from XML/object serialization. Add a legacy FreeOTP v1 adapter only if fixture provenance is explicit: deskOTP’s independent parser documents XML values containing JSON tokens with signed byte-array `secret`, `type`, `algo`, `digits`, `period`/`counter`. Current FreeOTP 2.x encrypted backup should return unsupported without a supplied password and compatible Keystore-independent envelope. |

## UI and migration workflow observations

- Ente, OTP Harbor, and deskOTP all converge on a review-before-commit flow: detect by content, show account identity and OTP parameters, classify duplicates/invalid/unsupported, then commit transactionally. AUTHENTICATOR DESK should keep secrets in Rust and return redacted preview rows.
- Aegis preserves groups, favorites, notes, icons, and UUIDs in its native vault; import should map only issuer/account/OTP parameters and treat foreign IDs as provenance metadata, never as local identity.
- 2FAS has explicit groups and ordering; retain group names/order only where the local model supports them. Ignore icon/service-type metadata unless a separately validated mapping exists.
- Ente’s local backups rotate up to five files and name them by timestamp; this is useful UX evidence for automatic-backup status, but its encrypted container is not a universal backup format.
- FreeOTP’s UI deliberately makes password-protected restore the gate; no UI should suggest that a file can be decrypted or bypassed without the user’s password.

## Windows security references for later work

The app requirements mention Windows Hello and DPAPI. These are capability/envelope references, not evidence that the feature is implemented. Use Microsoft’s `UserConsentVerifier.CheckAvailabilityAsync` and related Windows Hello API documentation to gate availability at runtime, and `CryptProtectData`/`CryptUnprotectData` (DPAPI) documentation for a user/machine-bound envelope. A DPAPI-wrapped automatic-backup key does not replace the independent backup password: password loss must still make password-encrypted portable backups unrecoverable. Record real Windows validation separately from source-level API presence.

## Recommended adapter interface and fixtures

Use an independent adapter interface such as `detect(bytes) -> Detection`, `preview(bytes, password?) -> MigrationPreview`, and `commit(selected_preview)`. Detection must be bounded, content-based, and reject ambiguous/malformed inputs. Every adapter returns normalized `AccountInput { kind, issuer, account, secret, algorithm, digits, period, counter }`; unsupported encrypted inputs return a stable `UnsupportedEncryptedFormat` error. Password prompts are explicit and cancellable; no password bypass or key guessing is attempted.

Fixtures must be synthetic or freshly generated: one valid and one malformed plaintext fixture per schema, one duplicate/unsupported-parameter case, one encrypted-without-password case, and (where implemented) one round-trip vector generated by AUTHENTICATOR DESK. Do not copy upstream account secrets, screenshots, test databases, or large license texts into the repository. Record fixture provenance and the exact upstream commit in the migration matrix.
