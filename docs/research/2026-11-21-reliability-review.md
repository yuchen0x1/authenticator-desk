# Reliability evolution: source review and ecosystem comparison

Research date: 2026-11-21 (Asia/Shanghai; 2026-11-20 UTC). Local baseline: `60dae05ec7cb1c7acc70255ae3faf3db695c743e`, package 0.2.1, latest published release v0.2.0. This is a source/documentation comparison, not a benchmark or independent cryptographic certification. Six public repositories were inspected using GitHub metadata, README, license, relevant source and test/workflow files. No third-party implementation, fixture, icon or branding was copied.

## Current capabilities and architecture

Authenticator Desk is an MIT-licensed, offline-first Windows authenticator. React 19/TypeScript renders a Tauri 2 WebView2 interface. Narrow native IPC calls Rust services; there is no HTTP listener, account server, cloud synchronization service or telemetry. SQLite schema 1 stores encrypted account metadata/seeds, preferences, categories and audit data. Argon2id derives the vault key and AES-GCM authenticates records. Session generations, revisions, a cooperating-process writer lease and expiry invalidate cached capabilities and decrypted previews.

The reviewed application supports TOTP/HOTP with SHA-1/256/512, configurable digits/period/T0, lossless decimal-string HOTP counters, explicit HOTP advancement, search, tags, categories, favorites, ordering and bulk operations. Imports cover otpauth lists, Google migration, plaintext Aegis/2FAS/andOTP and Ente URI lists; incompatible encrypted formats fail explicitly. Encrypted `.authdesk` backups support previewed Merge/confirmed Replace and ownership-proven automatic retention. Four locales, light/dark themes, compact/card/list views, keyboard-accessible modals, a favorites panel, tray/shortcut/startup integration and manually initiated signed updates are present.

Source review included all frontend business pages/components, IPC types, validation, translations and styles; all Rust vault/accounts/OTP/import/backup/clipboard/commands/update/security modules; relevant integration tests; manifests, lockfiles and CI/release scripts. Baseline execution independently passed 219 frontend, 108 Rust core and 38 Node release-trust tests. Source inspection is not proof of native UI or installer execution.

## Gap-to-implementation comparison

| Dimension | Baseline evidence | Reference lesson | This round / follow-up |
|---|---|---|---|
| Functional correctness | A failed edit can discard replacement-secret intent; future T0 aborts the complete display batch; malformed legacy numbers become defaults | Aegis/Stratum format contracts and KeePassXC parameter tests | Explicit replacement retry intent; available-only display path without weakening single-code validation; strict numeric parsing. |
| UI/UX | Auto-backup status is read once; timer failures are discarded by the caller | Ente local backup service and Extension backup state distinguish operations/results | Session-bound attempt/failure status, separate last success, safe 30-second refresh and explicit refresh control; preserve drafts and passwords across reads. |
| Performance/resource use | Each copied OTP starts a sleeping expiry thread | Mature service separation favors one bounded maintenance owner | One lazy clipboard worker per service, cancellable Condvar deadlines and bounded cleanup backoff. This is a structural resource bound, not a measured speedup. |
| Architecture | Native secret ownership and preview invalidation are already established | Separate converters/services from UI | Extend existing services; no new production dependency, cloud, database schema or backup format. |
| Security | Expiry cleanup has only one task-level attempt after the Windows backend's short open retry | Explicit ownership and lifecycle contracts | Retry only clear operations, preserving token and sequence checks. Do not change the intentional native protected-copy behavior under hidden display. |
| Extensibility | Google batches lack completeness tracking; no Stratum adapter | Ente batch tracker and Stratum public format specification | Next-round isolated features, not untested additions to this release. |
| Delivery | Some desktop tests are feature-gated out of routine CI; v0.2.0 currently has no installer assets | Explicit test/build/package lanes | Execute desktop-feature integration contracts; require exact-commit Security/CI, separate NSIS/MSI lifecycle checks, signatures and re-download verification before publishing. |

## Prioritized findings and next gates

No new P0 or proven cryptographic bypass was established. Initial priorities are impact estimates, not exploit scores.

- **P1, implemented in this round:** replacement-secret retry correctness; future-T0 display availability; strict legacy numeric import semantics; visible backup health; clipboard expiry retry. Integration and native acceptance evidence belongs in the [test report](../test-report.md), not inferred from implementation.
- **P2, next:** enforce shared account/category capacity at all transactional writes, not just backup encoding; support zero-account category/settings restores with explicit Replace consequences; improve import-commit error classification; qualify backup publication on non-NTFS media and crash durability; suppress Windows history/cloud inclusion with isolated OS acceptance.
- **P2, hardening research:** plain JSON/URL/QR/HMAC intermediates can outlive zeroizing wrappers. Inventory all copies before claiming lock-time memory erasure. This is not evidence of a recovered real seed or a broken encrypted-at-rest vault.
- **P3:** Google multi-QR completeness, keyboard-efficient quick-panel selection with IME safeguards, a specification-based Stratum plaintext adapter, optional issuer editing, default-algorithm/font-size UI, cold-start locale hints and OS-native ports with independent acceptance.
- **Delivery gates:** verify the exact new commit, not historical green checks; never run installer lifecycle tests against the user's active installation; preserve original schema edits; provision Authenticode identity only through explicit certificate/service authorization. Updater signatures are not Windows publisher signatures.

No startup/CPU/memory/import-throughput benchmark was run for competing applications. Their test files are evidence of test design, not proof those tests passed here. Their current branch links can move; recheck upstream before implementing a deferred integration.
