# AUTHENTICATOR DESK 设计规格

日期：2026-11-17
状态：已获用户批准，待规格审阅

## 1. 目标与边界

AUTHENTICATOR DESK 是一款离线优先的 Windows 桌面 2FA 管理器。第一阶段必须交付真正可运行的核心能力：加密保险库、TOTP/HOTP、账户管理、标准 URI 导入、加密备份恢复、基础安全审计和桌面 UI。摄像头识别、Windows Hello、系统托盘、全局快捷键、自动更新和安装包作为后续阶段实现，并分别记录是否完成真实环境验证。

项目不强制注册、不上传账户密钥、不依赖在线账号服务。网络时间校准只发送时间请求，不发送账户数据。

## 2. 技术方案

采用 Tauri 2、Rust、React、TypeScript、Tailwind CSS 和 SQLite。

Rust 负责：

- TOTP/HOTP 算法与时间基准。
- Argon2id 密钥派生。
- AES-256-GCM 加解密。
- 保险库会话、锁定、解锁和内存清理。
- SQLite 访问、迁移和完整性检查。
- URI、迁移文件和备份格式解析。
- Windows 桌面集成。

React 负责：

- 页面布局、导航和交互。
- 账户卡片、列表、搜索、分类和筛选。
- 导入预览、备份恢复预览和错误展示。
- 主题、多语言和可访问性。

前端不访问数据库文件，不持有主密码、派生密钥或账户 Secret 的持久化副本。所有敏感操作通过显式 Tauri Commands 完成。

## 3. 加密保险库

SQLite 保存版本化元数据和加密记录。账户 Secret、备注等敏感字段以 Rust 侧结构序列化后加密保存；每条记录使用独立随机 nonce，并使用稳定记录标识作为附加认证数据。主密码通过 Argon2id 派生会话密钥，参数和盐值保存于保险库头部，不保存主密码。

解锁时通过加密验证记录确认密码正确。锁定时清理 Rust 会话中的派生密钥、明文 Secret 和验证码缓存，并通知前端进入锁定状态。错误信息不得包含密钥、密码、明文备份内容或验证码。

备份使用独立密码和独立 Argon2id 参数，文件扩展名为 `.authdesk`。文件包含格式版本、KDF 参数、随机 nonce、加密载荷和完整性标签。恢复必须先解密、解析、校验并生成预览，再写入当前保险库。

## 4. 验证码引擎

实现 RFC 6238 TOTP 和 RFC 4226 HOTP：

- HMAC-SHA1、SHA-256、SHA-512。
- 6、7、8 位验证码。
- 可配置周期、T0 和 HOTP 计数器。
- 大整数时间戳和计数器的正确编码。
- Rust 侧统一时间基准。
- 前端每秒读取服务端状态，不自行维护长期计时基准。
- 系统休眠或明显时间跳变后重新获取状态。

测试必须覆盖 RFC 官方向量、不同位数、不同周期、边界时间、非法 Base32、非法参数和计数器回退保护。

## 5. 账户模型

账户字段包括：唯一 ID、平台名称、账户名称、Secret、算法、位数、周期、HOTP 计数器、分类、标签、备注、创建时间、修改时间、收藏状态和排序位置。

预置模板包括 GitHub、Google、Microsoft、Discord、Cloudflare、Amazon AWS、Steam、Facebook、Instagram、Binance 和自定义平台。模板只提供展示和辅助说明，不代表官方 API 集成。

账户服务提供新增、编辑、删除、批量删除、排序、收藏、分类移动、搜索、重复识别、详情查看、导入和导出。

## 6. 导入与迁移

第一阶段支持：

- `otpauth://` URI 单条和批量导入。
- 手动输入 Secret。
- 导入预览、参数校验、重复检测和失败原因。
- 标准二维码图片解析。

后续阶段逐个加入 Google Authenticator 迁移数据、Aegis、2FAS、andOTP、FreeOTP、Ente Auth 等格式。每种格式必须有真实样本、解析测试和明确的加密限制；未知或加密且没有密码的文件不得宣称支持或尝试绕过。

## 7. UI 结构

主窗口采用深色桌面应用布局：左侧导航、顶部状态区、内容区和操作反馈区。页面包括仪表盘、验证码中心、所有账户、收藏账户、分类管理、导入迁移、备份恢复、安全中心、操作日志和设置。

视觉系统使用深黑/深蓝底色、蓝紫强调色、玻璃质感面板、明确的焦点状态和有限的动作反馈动画。验证码卡片显示平台、账户、验证码、倒计时、环形进度、复制和收藏。所有主要按钮必须连接真实命令；空状态和错误状态必须提供下一步操作。

至少提供简体中文、繁体中文、英语和日语，语言资源集中管理，运行时可切换。

## 8. 桌面集成

后续阶段加入系统托盘、最小化到托盘、关闭行为、开机启动、锁定快捷操作、快速验证码面板、系统通知和自动更新检查。锁定状态下快捷面板不得显示验证码。Windows Hello 仅在当前系统 API 和权限满足时启用，未验证时不得标记为完成。

## 9. 测试与验收

必须建立 Rust 单元测试、前端组件测试和必要的集成测试。核心检查包括：

- RFC 4226/6238 向量。
- 账户 CRUD、搜索、分类、收藏和重复检测。
- 锁定、解锁、错误密码和敏感数据清理。
- 备份密码、篡改、损坏文件和恢复预览。
- URI、二维码、Base32 和参数错误。
- 时间跳变、休眠恢复和计数器回退。
- 日志敏感数据扫描。
- Windows Release 构建和安装包检查。

测试结果按 PASS、FAIL、PARTIAL、BLOCKED、NOT APPLICABLE 记录。构建成功不等于安装、签名、自动更新或真实端到端升级已经验证。

## 10. 交付顺序

1. 工程骨架、迁移系统和基础 UI。
2. Rust TOTP/HOTP 与测试向量。
3. 保险库、主密码和锁定。
4. 账户管理与 URI 导入。
5. 备份恢复与安全中心。
6. 二维码、迁移格式和剪贴板保护。
7. 托盘、快捷面板和 Windows 集成。
8. 多语言、主题、动画、文档和截图。
9. Release、MSI、NSIS、安装卸载验证和最终测试报告。

## 11. 明确限制

- 没有代码签名证书时，不报告已签名。
- 没有真实 Windows Hello、摄像头、安装升级和在线 Release 证据时，不报告已完成端到端验证。
- 主密码丢失时不能无损恢复原始 Secret；只能使用独立备份密码和可用备份恢复。
- 竞品只用于格式和产品研究，不直接复制其受许可证约束的代码。
