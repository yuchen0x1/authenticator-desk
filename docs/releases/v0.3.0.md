# v0.3.0 — Reliable codes, migrations and backup health

## New features / 新增功能

- Automatic-backup health now distinguishes the latest successful backup from the latest attempt and failure in the current unlocked session. Settings and Backup refresh the same native status every 30 seconds and offer an explicit refresh action. Refreshes preserve unsaved form values and do not count as vault activity.
- Future-start TOTP accounts display a localized not-active-yet state instead of making every other displayed code unavailable. They become available at T0; protected single-account generation still rejects a request before T0.

## Fixes / 修复

- Retain replacement-secret intent after a failed account edit while still clearing the sensitive input. Re-enter the new secret or explicitly cancel replacement before retrying; an empty retry can no longer silently keep the old secret and claim the replacement succeeded.
- Reject explicitly malformed Aegis, andOTP and 2FAS numeric parameters rather than replacing them with defaults. Absent-field defaults remain format-specific; HOTP counters retain the full unsigned 64-bit range without floating-point conversion.
- Retry expired clipboard cleanup after transient contention with token/sequence ownership protection. One cancellable worker replaces per-copy sleeping threads; clear retries use bounded backoff and never repeat a copy or erase a later user-owned value.
- Execute desktop-feature integration tests in Windows CI instead of merely compiling feature-gated shortcut contracts.
- Includes the previously unreleased 0.2.1 fixes: UTC clock correction/resume, cooperating-process vault writer exclusion, authenticated corrupt-row backup recovery, localized invalid-import reasons and stricter signed-release verification.

## Performance and architecture

No new production dependencies, server, database migration or backup format. Clipboard maintenance has a single-worker resource bound; no unmeasured startup, CPU or throughput speedup is claimed. Backup-attempt health is deliberately session-local; last-success metadata continues to use the existing encrypted configuration.

## Compatibility and upgrade

Windows x64 only. SQLite schema remains 1 and `.authdesk` encryption is unchanged. Existing valid imports remain supported; files containing explicit invalid numeric values must be corrected at their source rather than silently imported with different OTP semantics.

Before upgrading, create a verified encrypted backup and completely exit all application/tray instances, including older versions. Install the matching NSIS EXE or MSI family from this Release. Compare SHA-256 with `SHA256SUMS.txt`; `release-assets.json` records sizes and hashes. Signed builds also include installer signatures and a signed `update.json`, verified by the release pipeline against the independently configured public key. Preserve your vault data when uninstalling or recovering. See [update and recovery instructions](https://github.com/yuchen0x1/authenticator-desk/blob/main/docs/updating.md).

## Known limitations

- Updater/minisign signatures are not Windows Authenticode publisher signing; publisher identity remains unconfigured and SmartScreen may warn.
- Automatic-backup attempt/error state resets on lock, restart or reconfiguration. Last success survives restarts; enabling a new configuration resets its schedule. Permanent clipboard contention can exhaust the bounded retry budget; TTL cannot revoke third-party clipboard history/cloud copies.
- A genuine prior-version signed install → update → reopen-vault flow requires separate disposable-machine acceptance. Local source tests do not establish that scenario or non-Windows desktop support.
- Backup publication on FAT32/exFAT/network filesystems and shared write-capacity/backup-limit enforcement remain follow-up work. Unmaintained/target-irrelevant Rust dependency warnings remain documented; this release is not a claim of zero security risk.

## Verification

The tag pipeline must pass Security, portable Rust core tests, Windows frontend/Rust/updater/desktop tests, signed NSIS/MSI builds, separate clean-runner installer lifecycles, and cryptographic re-download checks before publishing. Exact observed local/remote results and remaining acceptance boundaries are recorded in `docs/test-report.md`.
